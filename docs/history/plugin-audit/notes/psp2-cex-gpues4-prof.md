What this is: a GPU (SGX543MP4 "GpuEs4") performance-counter profiler for retail Vitas. It is NOT an overlay: nothing in the repository draws, hooks a display function, or touches a framebuffer. It consists of (a) one kernel plugin that hooks five internal functions of the Sony `SceGpuEs4` driver and exports seven syscalls, and (b) user-side STATIC libraries that a developer links into their OWN application; those libraries intercept the application's GXM/vitaGL calls with GNU `ld --wrap`, not with taiHEN. Section 11 therefore describes what runs inside the (developer's) game process and its memory, and states "not applicable" for drawing.

## 1. Process context
- Module 1: `psp2_gpuprof.skprx`, kernel, `*KERNEL`: README.md:7 "Include `psp2_gpuprof.skprx` under `*KERNEL`"; `vita_create_self(psp2_gpuprof.skprx psp2_gpuprof CONFIG exports.yml UNSAFE)` (CMakeLists.txt:94); links `taihenForKernel_stub taihenModuleUtils_stub SceSysclibForDriver_stub SceSysmemForDriver_stub SceThreadmgrForDriver_stub SceProcEventForDriver_stub SceIofilemgrForDriver_stub` (CMakeLists.txt:88-90); all APIs are `ksce*`/`taiHookFunctionOffsetForKernel` (kernel.c:564); syscall exports `psp2_gpuprof: syscall: true` (exports.yml:10-11); `attributes: 0` (exports.yml:2). They live in the application's own process (the "game" is the developer's own app) in its .bss/stack; no taiHEN config section applies. `libpsp2_gpuprof_stub.a` is the syscall stub generated by `vita_create_stubs(... ## 2. Module start / stop
module_start (kernel.c:496-607), in order:
1. `startup_log("work-observations-v1", ...)` writes the first line of `ur0:tai/psp2_gpuprof.log` (kernel.c:506-510, 69-96): FILE I/O ON THE BOOT PATH, repeated at every subsequent stage (each call rewrites the whole accumulated report: open O_TRUNC, write, close, kernel.c:87-95).
2. `taiGetModuleInfoForKernel(KERNEL_PID, "SceGpuEs4", &mod)` (kernel.c:513); `< 0` -> `SCE_KERNEL_START_FAILED` with nothing to undo (kernel.c:515-516).
3. Driver fingerprint `mod.module_nid` must be 0xc0f361a3 or 0x237202cb else START_FAILED (kernel.c:517-522).
4. Four `module_get_offset` probes (text 0 and 0x104db, data 0 and 0x41e3 -- i.e. bounds checks that the segments are at least that large) via `startup_offset` (kernel.c:98-103, 523-527); any failure -> START_FAILED.
5. Eleven 8-byte code signatures compared with `memcmp` at fixed text offsets (kernel.c:480-493, 528-532), plus three extra fingerprints at 0x588e (6 B), 0x9eb8 (4 B) and 0x5760 (2 B) (kernel.c:536-545); mismatch -> `startup_log("signature-mismatch", ...)` + START_FAILED.
6. `gp_continuations_init(code_base)` fills the ten resume addresses used by the hand-written original-function trampolines (kernel.c:546; continuations.c:11-24).
7. Five driver-internal function pointers resolved by offset: `power_try` 0x4058, `power_unlock` 0x4040, `device_node` 0x9044, `power_lookup` 0x2cd4, `init_state` 0x4018 (kernel.c:548-552).
8. `gp_init(&session, &io)` (kernel.c:553), then `guard = ksceKernelCreateMutex("GpuProfGuard", 0, 0, NULL)`; `< 0` -> START_FAILED (kernel.c:554-556).
9. Loop over the five hooks (kernel.c:557-569): re-verify the 8-byte signature at the hook site right before patching ("Reject intervening patches rather than bypass another hook's chain", kernel.c:558-562); `taiHookFunctionOffsetForKernel(KERNEL_PID, &refs[i], mod.modid, 0, offsets[i], 1 /*thumb*/, functions[i])` (kernel.c:564-565); on `< 0`: `startup_error = hooks[i]; goto failed` (kernel.c:567); `resident = 1` after the first success (kernel.c:568).
10. `ksceKernelRegisterProcEventHandler("GpuProfOwner", &handler, 0)` with `exit` and `kill` = `on_exit` (kernel.c:570-576); failure -> goto failed.
11. Take the guard, set `ready = 1; startup_error = 0` unless `device_retired` was already set by a teardown hook racing startup (kernel.c:577-583), `startup_log("startup-result", ...)`, return `SCE_KERNEL_START_SUCCESS` (kernel.c:584-585).
`failed:` path (kernel.c:586-606): unregister the proc handler if registered (kernel.c:592-595); release hooks in REVERSE order guarded by `hooks[i] >= 0`, logging each result and clearing the slot only on success (kernel.c:596-601); then **if any hook had been installed (`resident`) it returns `SCE_KERNEL_START_SUCCESS` anyway and stays resident but disabled** ("Once code has been published, stay resident (disabled) until reboot", kernel.c:589, 603). Only when no hook was ever installed does it delete the mutex and return START_FAILED (kernel.c:604-606). In the resident-disabled state every syscall returns `startup_error` (kernel.c:327, 365, 383, 404, 428, 451, 470). `SCE_KERNEL_START_NO_RESIDENT` is never used.

module_stop (kernel.c:609-614): returns `SCE_KERNEL_STOP_CANCEL` unconditionally, "Explicit reboot-only lifetime; no unsafe live unloading of callbacks" (kernel.c:612). Nothing is released: 5 hooks, proc-event handler and the mutex live until reboot by design. There are no threads and no memblocks to free.

## 3. Hooks
All five hooks are `taiHookFunctionOffsetForKernel` into segment 0 of `SceGpuEs4` (`mod.modid`, thumb=1), installed in module_start (kernel.c:557-569), released only on the module_start failure path (kernel.c:596-601), never in module_stop. Original functions are NOT called through `TAI_CONTINUE`: the author replays the displaced prologue instructions by hand in naked asm and branches to the resume address because "Some taiHEN/substitute versions fail to" scale Thumb literal-load offsets (continuations.c:3-4); the hook sites "require exclusive ownership: kernel.c rejects patched entries" (continuations.c:7). `refs[i]` are therefore never dereferenced for calling (only passed to `taiHookReleaseForKernel`, kernel.c:598).

- Partial-failure handling: `hooks[]` is initialised to -1 (kernel.c:21); every install result is checked (kernel.c:567); release is reverse-ordered and guarded on `>= 0` (kernel.c:596-601); release results are checked and logged (kernel.c:598-600). The notable policy is that after any successful hook the module never returns START_FAILED (kernel.c:603) so taiHEN does not unload code that a driver thread may be executing.
- Hook bodies (all run on the driver's calling thread, kernel context): every body takes the `GpuProfGuard` mutex with `ksceKernelLockMutex(guard, 1, NULL)` (kernel.c:110-113) and returns driver error `0x18` (or `0x804c0018` for dump) WITHOUT calling the original if the lock fails (kernel.c:230, 240, 252, 265, 286). `misc_hook` passes through unless `misc[0] == 3`, then refuses the driver's own perf request with `0x18` while a session or dump is active (kernel.c:224-236). `pre_power_hook` restores counter selectors (`gp_invalidate(&session, old_state == 0)`) before letting the driver power down (kernel.c:238-248). `reset_hook` re-reads `registers = word(info, 0x14)` and invalidates (kernel.c:250-260). `dump_hook` increments `dumps_in_progress`, DROPS the guard before calling the original ("Do not hold our guard across" the original's OS-service calls, kernel.c:271-276) and re-takes it after. `teardown_hook` sets `device_retired=1; ready=0; startup_error=OFFLINE` before the original runs (kernel.c:291-293), then after it clears `registers=0` (kernel.c:300-309). No hook allocates, does I/O or sleeps; MMIO writes inside `gp_invalidate->restore` are 18 register writes (session.c:53-61). The reap path inside hooks calls `acquire()` which calls the driver's own `power_try(-3, 0)` -- a try-lock, "Never waits for a GPU lock" (kernel.c:192, 125). `startup_log` is never called from a hook ("Never log from GPU hooks", kernel.c:36).
- Syscall bodies: `ENTER_SYSCALL/EXIT_SYSCALL` (kernel.c:322, 350), `ksceKernelCopyFromUser` for inputs and `ksceKernelCopyToUser` for outputs (kernel.c:323, 337), take the guard, do bounded MMIO (Begin: ~5+16+1+5 reads, 1+16+1 writes, session.c:84-150; Read: 34 reads, session.c:37-51; Signals: per group 4 cores x 2 writes + 1 read, session.c:232-243). On `CopyToUser` failure after a successful Begin the lease is released immediately (kernel.c:339-343). Ownership is per process (`session.owner == ksceKernelGetProcessId()`, session.c:27-35) with a 64-bit never-recycled generation handle (session.c:80, 152).

## 6. Firmware assumptions
- No `ksceKernelGetSystemSwVersion`. The gate is the `SceGpuEs4` module NID: only 0xc0f361a3 and 0x237202cb are accepted (kernel.c:517-522); the analyzer treats 0xc0f361a3 as the known-good fingerprint (tools/analyze.py:437, 673). Source comments repeatedly say "retail 3.65" (identity.h:11, capture.h:88, lab/capture.c:49-50, vitagl-scene/main.c:129). Which firmware 0x237202cb corresponds to is not stated in source.
- One single offset table (no per-firmware variants): hook sites 0x5e68/0x63f8/0x5758/0x9b58/0x4674 (kernel.c:500), resume points (continuations.c:13-22), helper functions 0x4018/0x4040/0x4058/0x2cd4/0x2d94/0x9044 (kernel.c:481-486, 548-552), data offsets 0x41e0/0x20/0x08/0x54/0x1c/0x14/0x20/0x7f4 and scheduler state offsets 0x108-0x148 (kernel.c:127-138, 157-170), segment size floor 0x104db text / 0x41e3 data (kernel.c:524-526). Every code offset that is executed or patched is byte-fingerprinted first (kernel.c:481-493, 528-545, 559); the data offsets are only sanity-checked by `ksceKernelIsAccessibleRange(3, ...)` at use (kernel.c:155-162) and by the `!sys || !node` style null checks (kernel.c:128-137). On any other firmware the module logs `driver-fingerprint`/`signature-mismatch` and returns START_FAILED without patching anything (kernel.c:521-545).
- Hardware assumption: SGX543MP4, 4 cores at `0x8000 + c*0x4000`, 8 counters, register 0x4000 must read `& 3 == 3` else UNSUPPORTED (session.c:7-9, 84-90); perf-control must be 0 or 0xff (session.c:103-120). `info.cores = 4; info.counters = 8` hard-coded (kernel.c:403-404).
- No on-device test harness in source; the optional `GPUPROF_BEGIN_DIAGNOSTIC` build logs the first Begin result (CMakeLists.txt:80-83, kernel.c:42-67) and the unit tests run against a simulated register file (tests/session_test.c:7-50).

## 7. Configuration
- None for the kernel module: no file is read (the only `ksceIoOpen` calls are the two log writers, kernel.c:59, 87). Behaviour is fixed at compile time (`GPUPROF_BEGIN_DIAGNOSTIC`, CMakeLists.txt:80-83). Per-request configuration comes from the calling app through the syscall argument structs, validated for `size`/`abi`/reserved-zero/ranges (session.c:70-77, 208-215; diagnostic.c:7-13, 33-40; kernel.c:449).
- User libraries: configured programmatically (`psp2GpuProfCaptureInit` with caller storage, `psp2GpuProfGxmSetObserver`, `psp2GpuProfVitaGLCapture`, capture.h:70-76, gxm_observer.h:49-53, vitagl.h:9-10). Examples write CSVs under `ux0:data/` (e.g. draw_probe.c:113-115, lab/capture.c:369-371).

## 8. Logging
- Kernel: `startup_log` (kernel.c:69-96) accumulates fixed-format lines (`<stage> 0x%08x 0x%08x\n`, hand-rolled hex, no printf) into the 4 KiB static `report` and, on EVERY call, re-opens `ur0:tai/psp2_gpuprof.log` with `SCE_O_WRONLY|SCE_O_CREAT|SCE_O_TRUNC`, writes the whole buffer (up to 8 write attempts) and closes (kernel.c:87-95). A successful boot performs this ~22 times (one per `startup_log` call in module_start: kernel.c:506/510, 514, 518, 101 x4, 533, 547, 555, 563+566 x5, 575, 584) -- all on the boot path, synchronous, in kernel context. Cap: 4,096 B total, lines beyond are silently dropped (kernel.c:85); no rotation (truncate-on-write). Never called from hooks or syscalls (kernel.c:36). Optional `begin_report` (compile-time `GPUPROF_BEGIN_DIAGNOSTIC`) writes exactly one 62-byte line to `ur0:tai/psp2_gpuprof_begin.log` from the first completed `psp2GpuProfBegin`, outside the guard (kernel.c:42-67, 347-349).
- User libraries: no logging. `psp2GpuProfCaptureWriteCsv` writes to a caller-opened `FILE*` only after `Stop` ("never opens or closes files", capture.h:104; client_capture.c:111-133).
- Examples: CSV/status files under `ux0:data/...` opened by the app, written after sampler join (draw_probe.c:113-115, 157-176; lab/capture.c:369-371).

## 10. Patterns worth copying / anti-patterns
- Copy: fingerprint-before-patch at three levels (module NID, 11+3 byte signatures across the module, and a re-check of the exact 8 bytes at each hook site immediately before `taiHookFunctionOffsetForKernel`) so a foreign hook on the same site is detected instead of chained through (kernel.c:517-545, 558-562).
- Copy: `hooks[] = {-1,...}` initialiser, reverse-order guarded release, each release result logged, slot cleared only on success (kernel.c:21, 596-601).
- Copy: the "once code is published, stay resident disabled rather than unload" decision and `module_stop -> SCE_KERNEL_STOP_CANCEL` with the reasoning written next to the code (kernel.c:588-591, 603, 612-613). For a plugin patching a driver that may be mid-call on another CPU this is the safe choice; the cost is that a failed start leaves a hooked but inert driver until reboot.
- Copy: never hold your own guard across a call into the original when the original takes OS locks (`dump_hook`, kernel.c:271-276); use the driver's own try-lock (`power_try`) and bail with BUSY instead of waiting (kernel.c:125, 192-194).
- Copy: per-process lease with a never-recycled 64-bit generation and release-on-process-exit via `ksceKernelRegisterProcEventHandler` (session.c:27-35, 80, 152; kernel.c:210-222, 570-574); release of the lease when `ksceKernelCopyToUser` fails so a client can never strand it (kernel.c:339-343).
- Copy: all MMIO pointer chains validated with `ksceKernelIsAccessibleRange` and `dmb/dsb` fences around volatile register access (kernel.c:155-162, 174-190); kernel code compiled `-mgeneral-regs-only -mno-unaligned-access` (CMakeLists.txt:77-78, 85-86).
- Copy: user-side recorder with caller-owned fixed storage, drop counter, all-or-none batch insert, zero allocation and no syscalls in the hot path (client_capture.c:13-22, 45-50, 66-91).
- Anti-pattern: ~22 synchronous open/truncate/write/close cycles to `ur0:tai/psp2_gpuprof.log` during module_start on the kernel boot path (kernel.c:87-95 called at kernel.c:506-584). One write at the end (or a ring in memory) would do; a slow/failing `ur0:` lengthens boot.
- Anti-pattern (deliberate, but worth flagging): hand-written naked-asm replays of the displaced prologues instead of `TAI_CONTINUE` (continuations.c:40-74). They are correct only for exactly those 2 driver builds and make the plugin depend on the patch size taiHEN/substitute chooses (8 bytes, continuations.c:56-57).
- Anti-pattern: no release of hooks/handler/mutex in module_stop (kernel.c:609-614); acceptable only because the author explicitly declares a reboot-only lifetime.
- Anti-pattern: returning driver error `0x18` from `misc_hook` to the driver's own perf-counter request while a user session is active (kernel.c:231-233) changes the behaviour of Sony code paths (e.g. a retail diagnostic dump) for the whole system while any app holds a lease.

## 11. Overlay-specific
Not an overlay: nothing draws, nothing hooks `sceDisplaySetFrameBuf`, no framebuffer/text/font buffers exist anywhere in src/ (grep for `Display`, `FrameBuf`, `vita2d`, `paf` in src/: none; vita2d appears only in the example apps' own rendering, e.g. draw_probe.c:4, 42-57). What runs inside the game process and its memory:
- Only code the developer links into their OWN game: the `--wrap`ped `sceGxm*` entry points (gxm_observer.c:27-240) and `gl*` entry points (vitagl_capture.c:25-97). Each wrapper reads `sceKernelGetThreadId()` and `sceKernelGetSystemTimeWide()` twice (gxm_observer.c:15-16, 20), fills a 60-byte stack struct, calls the real function, and invokes the app's observer callback -- "The callback must not call GXM" (gxm_observer.h:50). When no observer is set the wrapper is a direct tail call (`if (!observer) return __real_...`, gxm_observer.c:29). The recorder copies 248 B per event into caller-provided storage under the caller's mutex (client_capture.c:45-66).
- Where the bytes come from: the game's own .bss or heap (whatever the developer passes as `Psp2GpuProfCaptureConfig.events`, capture.h:71-72; examples use `static` arrays, submission_capture.c:12). Allocated at compile/link time (static) by the examples; nothing is allocated lazily or per frame by the libraries; freed never (process lifetime; "process exit eventually reclaims everything", standalone-vitagl/main.c:69-71).
- GPU memory: the plugin and libraries allocate none. The probes allocate `USER_RW_UNCACHE` blocks for their own transfer workloads (isolation_probe.c:154, transfer_probe.c:74) -- test payload, not profiler state.
- Kernel side per sample: ~36-350 bytes of caller kernel stack; MMIO reads/writes to the SGX register window `registers` obtained from the driver's device info under `power_try` (kernel.c:126-139) -- no mapping is created by the plugin.
- What happens when the game has no memory left: nothing new is requested, so nothing fails -- the recorder returns `PSP2_GPUPROF_CAPTURE_FULL` and counts `dropped` when its fixed ring is full (client_capture.c:45-48), the trace returns BUSY and counts (client_trace.c:37-40), the GXM state cache sets `incomplete` (client_gxm_state.c:19-28), and the kernel syscalls carry no allocation at all. The only process-level memory impact is the developer's own choice of ring size (1 MiB..32 MiB in the examples) plus a 64 KiB sampler stack if they follow the examples (draw_probe.c:137-138).
